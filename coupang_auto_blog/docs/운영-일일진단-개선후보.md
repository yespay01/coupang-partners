# 일일 진단과 개선 후보 운영

> 목적: 일별 측정 데이터에서 데이터 품질 이상과 다음 실험 방향을 제안한다.
>
> 이 시스템은 UI·콘텐츠·상품 순서·링크 목적지를 자동 변경하지 않는다.

관련 설계: [CTR·상품 큐레이션·자동 개선 설계서](./plans/CTR-상품큐레이션-자동개선-설계서_2026-08-25.md)의 13~15절.

## 현재 입력 계약

`daily_metric_rollups`의 overall 1행/일만 읽는다.

| 필드 | 의미 |
|---|---|
| `business_date_kst` | KST 사업일, PK |
| `eligible_impression_sessions` | 실제 카드·CTA를 본 적격 세션 |
| `qualified_outbound_sessions` | eligible 세션과 outbound 세션의 교집합 |
| `raw_outbound_sessions` | 필터 전 outbound 세션 |
| `orphan_outbound_sessions` | 페이지·링크 문맥 연결 실패 세션 |
| `qualified_outbound_ctr_pct` | 0~100 백분율 |
| `impression_events`, `outbound_events`, `total_events` | 원천 이벤트 수 |
| `bot_events`, `duplicate_events` | 봇 이벤트 수와 동일 이벤트 ID 재전송 감지 수. 중복 플래그는 원본 이벤트의 CTR 제외 조건이 아님 |
| `source_max_received_at` | 원천 이벤트 watermark |
| `data_status` | `complete`, `partial`, `no_data` |

현재 rollup에는 surface와 device 차원이 없다. 따라서 생성 결과의 `surfaceAvailability`는 `not_available`이며, 홈·상세·검색 중 어느 화면이 원인인지는 단정하지 않는다.

## 후보 생성 원칙

- `no_data`는 성과 0이 아니라 데이터 품질 장애로 분류
- `partial` 데이터로 성과 방향을 만들지 않음
- 하루 eligible 세션 100 미만이면 `insufficient_daily_sample`만 제안
- 14개 연속 complete 일자가 없으면 UI 실험 방향 보류
- 봇 20%, 중복 15%, orphan 5% 초과 시 품질 후보 생성 및 UX 후보 억제
- 최근 이벤트가 48시간 이상 오래되면 stale 후보 생성
- 최근 7일 CTR이 직전 7일보다 0.5%p 이상 및 상대 20% 이상 하락한 경우에만 하락 대응 실험 제안
- CTR 하락이 없어도 14일 기준선이 준비되면 첫 단일 변수 실험을 백로그로 제안
- 하루치 상승으로 승자를 선언하지 않음

모든 후보는 다음 값을 반드시 포함한다.

- 기준선과 현재 근거 `evidence`
- 분석 기간과 eligible/converter 표본 `sample`
- primary metric과 불확실성
- 데이터 품질, EPC, 취소율 등의 `guardrails`
- 즉시 원상 복구할 `rollbackPlan`
- 정책·데이터 위험
- `status: proposed`
- `winnerDeclared: false`
- `requiresHumanApproval: true`
- `automaticChangeAllowed: false`

EPC와 취소율은 현재 daily rollup에 없다. UX 후보에서는 두 guardrail을 `not_available`, `blocksApproval: true`로 기록한다. 이 값이 결합되기 전에는 후보를 승인하면 안 된다.

## 상태

| 상태 | 의미 |
|---|---|
| `proposed` | 사람 검토 대기 |
| `approved` | 제안 방향 검토 완료. 배포 승인이 아니며 별도 구현 절차 필요 |
| `rejected` | 근거·우선순위·위험을 검토해 거절 |
| `expired` | 새 제안이 대체했거나 유효기간 만료 |

허용 전이는 `proposed → approved/rejected/expired`, `approved → expired`다. 승인·거절에는 `reviewedBy`가 필요하다.

같은 `candidate_key`로 새 날짜의 proposed 후보를 저장할 때 과거 proposed 행은 먼저 `expired`로 바뀐다. 이미 approved/rejected 된 행은 덮어쓰지 않는다.

## 안전한 JSON dry-run

운영 DB를 연결하지 않고 fixture로 제안서를 확인한다.

```bash
cd automation-server
node scripts/generate-improvement-candidates.js \
  --input test/fixtures/daily-rollups-sample.json \
  --output /tmp/improvement-candidates.json \
  --business-date 2026-08-24
```

CLI는 입력 JSON만 읽고 지정한 JSON 파일만 새로 만든다. 기존 파일은 덮어쓰지 않으며 DB, Slack, UI, 콘텐츠를 호출하지 않는다.

## 서비스 사용

주요 export:

- `normalizeDailyMetricRollup(row)`
- `generateImprovementCandidates(rows, options)`
- `fetchDailyMetricRollups(db, options)`
- `persistProposedCandidates(db, candidates)`
- `runImprovementCandidateJob(db, options)`
- `validateImprovementCandidate(candidate)`
- `transitionImprovementCandidate(candidate, status, review)`

`runImprovementCandidateJob`은 기본 `persist: false`이므로 dry-run이다. 후보 테이블 저장이 명시적으로 승인된 작업에서만 `persist: true`를 전달한다. 저장하더라도 `improvement_candidates` 외의 상품·리뷰·UI 테이블은 변경하지 않는다.

`persist: true` coordinator는 다음 운영 계약을 따른다.

- `pg_try_advisory_xact_lock`으로 동일 사업일 중복 실행 방지
- `job_runs.job_name = daily_improvement_candidates`
- `(job_name, business_date_kst)` 충돌 시 attempt 증가와 상태 갱신
- 성공 시 후보 수, 저장 수, 데이터 상태, `automaticChangesApplied: false`를 metadata에 기록
- 실패 시 오류 코드를 최대 500자로 제한해 기록
- 같은 날짜 재실행은 동일 candidate key를 upsert하므로 행이 중복되지 않음
- 트랜잭션은 후보와 job 상태만 변경하며 UI·상품·리뷰·설정을 변경하지 않음

## 마이그레이션

```text
automation-server/db/migrate-improvement-candidates.sql
```

마이그레이션은 다음을 DB CHECK로 고정한다.

- 상태 enum-like 제약
- evidence/sample/guardrails/rollback 필수
- `winner_declared = FALSE`
- `requires_human_approval = TRUE`
- `automatic_change_allowed = FALSE`
- `(candidate_key, business_date_kst)` unique

이 작업에서는 운영 DB에 마이그레이션을 실행하지 않았다.

## 검토 절차

1. 데이터 품질 후보를 먼저 처리한다.
2. quality 후보가 있으면 UX 후보 승인을 보류한다.
3. 표본과 14일 complete 조건을 확인한다.
4. EPC·취소율·오류율 guardrail을 결합한다.
5. 한 surface에서 한 변수만 바꾸는 실험 계획인지 확인한다.
6. control과 rollback 절차를 실행 전에 검증한다.
7. 승인 후에도 구현·배포는 별도 작업으로 수행한다.
