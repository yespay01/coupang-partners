# 세모링크 CTR 극대화 및 일일 자동 개선 시스템 설계서

> 작성일: 2026-08-25
> 상태: 조사·기획 완료, P0·P1 추적 기반과 P2 내부 이벤트 일일 진단·개선 후보의 로컬 구현·검증 완료. 상품 필터, 쿠팡 리포트 결합, 실험 실행, 가격 알림은 미구현
> 핵심 목표: 세모링크 방문자가 신뢰할 수 있는 상품 선택 정보를 얻고 쿠팡 제휴 링크를 클릭하도록 돕는다.

## 0.1 2026-08-25 구현 체크포인트

이번 작업에서 P0 중 코드로 즉시 막을 수 있는 항목을 먼저 반영했다.

- Product API 제휴 URL의 Partner ID와 `lptag` 일치 검증
- 일반 쿠팡 URL만 Deep Link API로 변환하고 응답 `landingUrl` 재검증
- 빈 `subId`를 Partner ID로 대체하지 않는 회귀 테스트
- 공개 제휴 링크의 공통 `sponsored nofollow noopener noreferrer` 처리
- 페이지 첫 제휴 링크 전 한 줄 고지와 CTA별 중복 고지 제거
- 홈 상품 카드의 내부 상세 링크와 쿠팡 직접 CTA 분리
- 근거 없는 `최저가`, 회원 할인, 로켓배송 문구 제거
- 허위 구매·사용·배송·포장 경험 프롬프트 제거와 생성 결과 차단
- 품질 검증 실패 생성문의 저장 중단
- 임의 평점 4.5, `Offer`, `InStock` 구조화 데이터 제거

이어진 P1 로컬 작업에서는 다음 추적 기반도 반영했다.

- UUID 기반 `affiliate_links` registry와 검증된 `/go/{link_id}` 302 경로
- 브라우저에 원본 목적지를 넣지 않는 same-origin `/go` 링크
- 클릭 직전 Partner ID·허용 hostname·활성·검증 상태 재확인
- `page_view`, `list_view`, 카드·CTA 노출, `outbound_click` 원천 이벤트
- HttpOnly 익명·세션 ID와 서버 HMAC 저장, raw IP·전체 referrer 미저장
- KST `business_date_kst`, 이벤트 UUID 중복 제거, 봇 표시
- 기존 `coupang_clicks` 이중 기록과 봇 클릭 제외
- 기존 상품·리뷰 링크의 기본 dry-run 백필 도구
- 기존 리뷰의 허위 체험·가격·효능·상품 불일치 읽기 전용 감사 도구

P2 로컬 작업에서는 다음 진단 기반도 반영했다.

- KST 사업일별 overall Qualified CTR rollup과 최근 7일 멱등 재집계
- 무데이터·고아 outbound·봇·중복 재전송 이상 진단
- 표본·14일 연속 complete·EPC·취소율 guardrail을 적용한 개선 후보
- `proposed/approved/rejected/expired` 상태 계약과 자동 변경 금지 DB 제약
- 기본 OFF인 04:20 KST 일일 coordinator와 작업 이력
- 관리자 분석 화면의 읽기 전용 rollup·이상·후보·작업 상태

아직 구현하지 않은 범위는 P1의 가격대·용도·검증된 배송 필터, P2의 쿠팡 리포트·EPC·취소 결합, surface별 분석과 실제 A/B 배정·승인 실행, P3 이후 가격 이력과 가격 알림이다. 배포, 운영 DB 마이그레이션, 백필, 운영 콘텐츠 감사, Slack 전송도 이번 로컬 작업에 포함하지 않았다.

> 사업 KPI: 쿠팡 아웃바운드 클릭 수가 아니라 취소 반영 수익과 방문 세션당 수익을 지속적으로 높인다.

## 1. 결론

세모링크는 `AI 사용후기 블로그`에서 `쿠팡 상품 선택·딜 큐레이션 서비스`로 전환해야 한다.

권장 제품은 다음 세 기능의 조합이다.

1. **상품 모음형 쇼핑 UI**로 방문자가 첫 화면에서 후보를 빠르게 훑게 한다.
2. **가격대·용도·단가·배송·주의점 기반 큐레이션**으로 쿠팡 상품 피드에 없는 추가 가치를 제공한다.
3. **매일 성과를 진단하고 다음 실험을 추천하는 시스템**으로 개선을 누적한다.

가격 알림은 매력적이지만 현재 API와 데이터 구조만으로는 정확한 가격 하락을 보장할 수 없다. 먼저 4주 이상 가격 관측 신뢰도를 검증한 뒤 베타 기능으로 추가한다.

또한 `매일 점검`과 `매일 자동 변경`을 구분해야 한다. 현재 트래픽에서는 하루치 결과로 문구와 배치를 바꾸면 우연을 학습하게 된다. 시스템은 매일 데이터를 수집·검증·분석하되, 충분한 표본이 쌓였을 때만 승자를 판단해야 한다.

## 3. 현재 기준선

### 3.1 콘텐츠와 상품

| 항목 | 현재 값 |
|---|---:|
| 수집 상품 | 450개 |
| 공개 리뷰 | 395개 |
| 공개 비율 | 100% |
| 가격·제휴 URL·대표 이미지 누락 상품 | 0개 |
| 경험을 주장하는 리뷰 | 213개, 53.9% |
| `내돈내산`을 명시한 리뷰 | 18개, 4.6% |

경험 주장 집계는 `직접`, `써보`, `사용해`, `먹어보`, `배송`, `택배` 등의 표현을 기준으로 한 보수적인 텍스트 검사다. 실제 구매 증빙은 시스템에 없다.

### 3.2 방문과 클릭

| 기간 | 전체 페이지뷰 | 리뷰 페이지뷰 | 로컬 쿠팡 클릭 | 거친 리뷰 CTR |
|---|---:|---:|---:|---:|
| 최근 24시간 | 56 | 47 | 3 | 6.38% |
| 최근 7일 | 364 | 293 | 9 | 3.07% |
| 최근 30일 | 1,775 | 1,425 | 28 | 1.96% |

`1.96%`는 현재 화면의 대략적인 기준선일 뿐 실험 판단용 지표가 아니다. 페이지뷰와 클릭이 세션 기준으로 중복 제거되지 않았고, CTA가 실제 화면에 보였는지 알 수 없으며, 봇·내부 이동·추적 누락이 완전히 보정되지 않았다.

방문 추적은 2026-03-03에 시작했지만 클릭 추적은 2026-07-14에 시작했다. 따라서 전체 기간 클릭률은 계산하면 안 된다.

### 3.3 클릭 위치

| 위치 | 최근 30일 클릭 | 비중 |
|---|---:|---:|
| 상단 CTA | 11 | 39.3% |
| 상품 이미지 | 10 | 35.7% |
| 하단 카드 | 4 | 14.3% |
| 하단 고정바 | 3 | 10.7% |
| 본문 중간 CTA | 0 | 0% |

상단 CTA와 이미지가 클릭의 75%를 차지한다. 이는 첫 화면이 중요하다는 강한 신호지만, 위치별 노출 분모가 없으므로 상단 CTA가 다른 위치보다 통계적으로 우수하다고 단정할 수는 없다.

현재 `mid` 클릭이 없는 이유 중 하나는 본문 중간 CTA가 비어 있지 않은 문단 8개 이상에서만 생성되는데 최근 글 대부분이 그보다 짧기 때문이다.

### 3.4 유입 구조

최근 30일 기준 전체 1,775 페이지뷰 중 리뷰 상세가 1,425회이고 홈은 80회다. 검색 랜딩 상세 페이지가 사실상 주 진입점이다.

| 유입 표기 | 페이지뷰 | 비중 |
|---|---:|---:|
| direct | 1,507 | 84.9% |
| 모바일 네이버 | 208 | 11.7% |
| PC 네이버 | 51 | 2.9% |
| 기타 | 9 | 0.5% |

다만 SPA 경로 변경 때 `document.referrer`를 반복 사용하는 구조라 최초 획득 채널과 내부 이동이 분리되지 않는다. `direct 84.9%`를 실제 직접 유입으로 그대로 해석해서는 안 된다.

## 4. 가장 큰 문제

### 4.1 허위 체험과 상품-본문 불일치

최근 공개 30건 표본에서 최소 5건의 명백한 의미 불일치가 발견됐다.

- 제주삼다수 500ml 20개를 뚜껑이 있는 장난감 수납함처럼 설명
- 금·은 클리너를 옷 보풀 제거기처럼 설명
- 버블클렌저를 아기 세제로 설명
- 업소용 카운터를 신발 수납 벤치처럼 설명
- 의류용 고무 밴드를 소파 커버처럼 설명

카테고리도 월계수잎 맛술과 주얼리 보관함이 `남성패션`으로 수집되는 사례가 있다. 이런 오류는 CTA 문구보다 먼저 방문자의 신뢰를 무너뜨린다.

원인은 기본 프롬프트가 실제 구매·사용 자료 없이도 배송, 포장, 사용 장면, 장단점, `내돈내산` 같은 서사를 만들도록 요구하는 데 있다.

- `automation-server/src/services/settingsService.js`
- `automation-server/src/services/reviewUtils.js`
- `automation-server/src/routes/review.js`

### 4.2 입증할 수 없는 가격·혜택·평점 표현

현재 화면과 메타데이터에는 다음 표현이 있다.

- `직접 써보고 골라낸`
- `최저가`
- `회원 전용 추가 할인가 보기`
- `로켓배송 가능`
- 구조화 데이터 평점 `4.5`
- 구조화 데이터 재고 `InStock`

그러나 현재 DB에는 실제 사용 증빙, 외부 판매처 비교, 회원 추가 할인, 평점, 재고 상태가 없다. API가 반환하는 `isRocket`, `isFreeShipping`도 현재 저장하지 않는다.

따라서 화면과 SEO 데이터가 실제 근거와 일치하지 않는다.

### 4.3 클릭 경로가 길다

현재 홈 상품 카드는 `쿠팡 최저가 보기`라고 표시하지만 실제로는 리뷰 상세로 이동한다.

```text
현재: 홈 상품 카드 → 긴 AI 후기 → 쿠팡
권장: 홈 상품 카드 → 쿠팡
      비교가 필요한 경우만 → 비교 페이지 → 쿠팡
```

쿠팡 클릭이 1차 목적이라면 기본 경로는 한 단계여야 한다. 다만 SEO와 선택 지원이 필요한 컬렉션에는 `비교 보기`와 `쿠팡에서 현재 가격 확인`을 명확히 분리한다.

### 4.4 CTA가 많지만 선택 이유가 없다

리뷰 상세 한 페이지에 이미지, 상단, 중간, 하단, 고정바까지 최대 5개의 CTA가 있다. 모두 비슷한 `최저가` 문구를 반복한다.

방문자는 버튼을 못 찾아서 클릭하지 않는 것이 아니다. 다음 질문에 답을 얻지 못해 클릭하지 않는다.

- 이 상품이 내 용도에 맞는가?
- 비슷한 상품보다 무엇이 낫거나 불리한가?
- 현재 보이는 가격이 언제 확인된 것인가?
- 용량과 수량을 고려하면 실제 단가는 얼마인가?
- 배송 정보는 실제 확인된 것인가?
- 왜 세모링크가 이 상품을 골랐는가?

### 4.5 얇은 제휴 페이지 위험

상품 API 결과를 그대로 카드로 나열하는 것만으로는 해결되지 않는다. Google은 원 판매처와 차별되는 정보나 기능이 없는 대량 제휴 페이지를 `thin affiliation` 위험으로 설명한다.

세모링크가 추가해야 할 고유 가치는 다음과 같다.

- 단위당 가격
- 실제 관측 가격과 확인 시각
- 용도·예산·배송 기반 필터
- 같은 목적의 대안 비교
- 추천 대상과 피해야 할 대상
- 데이터 기반 인기 또는 가격 변화
- 공개된 선정 기준과 오류 정정 절차

### 6.2 홈

홈은 최신 리뷰 100개를 나열하는 대신 아래 순서로 구성한다.

1. 검색과 핵심 가치 제안

다이나믹 배너는 최상단 기본 요소가 아니라 비교 실험 대상으로 둔다.

### 6.3 초기 집중 카테고리

초기에는 반복 구매와 비교가 쉬운 네 영역에 집중한다.

- 생활·세탁
- 식품·음료
- 주방·정리
- 반려동물 소모품

패션은 옵션·사이즈·반품 문제가 많고, 고가 가전은 스펙과 가격 비교 정확도가 중요하다. 건강 효능 상품은 허위·과장 위험이 크므로 데이터와 검수 체계가 갖춰지기 전에는 후순위로 둔다.

### 6.4 추천 컬렉션 예시

- 1만원 이하 세탁·청소용품
- 생수 500ml 묶음 구성 비교
- 한 달에 다시 사는 주방 소모품
- 고양이 모래·사료 가격대별 모음
- 캠핑에서 바로 먹기 쉬운 간편식
- 아이 연령별 활동책
- 로켓배송이 실제 확인된 급한 생필품
- Goldbox 오늘의 상품

## 8. 쿠팡 API 활용 가능 범위

현재 프로젝트는 다음 API를 이미 사용한다.

- Goldbox 상품
- 카테고리별 베스트
- 키워드 검색
- 쿠팡 PL 및 PL 브랜드
- 딥링크
- 클릭·주문·취소·수익 리포트

현재 로컬 문서 기준 주요 제약은 다음과 같다.

- Goldbox는 매일 오전 7:30 갱신
- 키워드 검색은 분당 최대 50회
- 키워드 검색 상세 상품은 응답당 최대 10개

- 파트너스 실적 리포트는 익일 오후 반영을 고려해야 함
- 등록되지 않은 `subId`는 정산에서 제외될 수 있으므로 운영 전에 채널 등록 확인 필요

현재 DB와 수집 로직에는 다음 한계가 있다.

- `isRocket`, `isFreeShipping` 미저장
- 가격 관측 시각과 이력 없음
- 동일 `productId` 재수집 시 갱신하지 않고 건너뜀
- 판매자·옵션·vendorItem 정체성 미보존
- 정가·할인율·재고·평점 정보 없음

따라서 현재 데이터만으로는 `인터넷 최저가`, `할인율`, `재고 있음`, `가격 하락`을 주장할 수 없다.

## 9. 정확한 성과 지표

### 9.1 1차 지표

**Qualified Unique Outbound CTR**

```text
쿠팡 링크를 한 번 이상 클릭한 적격 세션 수
────────────────────────────────────────── × 100
실제로 상품 카드 또는 CTA를 본 적격 세션 수
```

한 세션에서 CTA를 여러 번 클릭해도 전환 세션은 1로 센다. 따라서 지표는 100%를 넘을 수 없다.

### 9.2 보조 지표

- 페이지 아웃바운드 CTR
- 상품 카드 CTR
- CTA 위치별 CTR
- 로컬 클릭 대비 쿠팡 검증 클릭 비율
- 쿠팡 클릭 대비 주문 전환율
- 취소 반영 순주문 전환율
- 클릭당 수익 EPC
- 적격 세션당 순수익
- 카테고리·surface별 순수익

### 9.3 최종 판단 원칙

CTR만 높이면 클릭베이트가 승자가 될 수 있다. 실험 승격은 다음 조건을 함께 본다.

- Qualified Unique Outbound CTR 상승
- 쿠팡 검증 클릭 비율이 악화되지 않음
- 주문 전환율 또는 EPC가 악화되지 않음
- 취소율이 상승하지 않음
- 페이지 속도와 오류율이 악화되지 않음
- 가격·배송·상품 정보 정확성이 유지됨

## 11. 공통 제휴 링크 추적

리뷰뿐 아니라 홈, 컬렉션, 검색, 레시피, 기존 상세, 가격 알림의 모든 쿠팡 링크가 같은 추적 체계를 사용해야 한다.

### 11.1 제휴 ID 원칙

기존 [쿠팡 링크 체계 문서](../쿠팡-링크-체계.md)와 현재 코드를 기준으로 한다. 새 추적 시스템이 쿠팡 링크 생성 방식을 다시 만들지 않는다.

현재 구조:

```text
상품 검색·Goldbox·카테고리·PL API
  → 쿠팡이 제휴 정보가 포함된 productUrl 반환
  → product_url과 affiliate_url에 그대로 저장
  → 별도 Deep Link 변환 없음

관리자가 입력한 순수 www.coupang.com URL
  → 기존 /api/admin/deeplink
  → Deep Link API 변환
  → shortenUrl 사용, landingUrl로 제휴 정보 검증 가능
```

쿠팡 링크에는 서로 다른 두 식별 개념이 있으므로 혼동하지 않는다.

| 구분 | 역할 | 검증 방법 |
|---|---|---|
| 파트너 추적 코드 | 최종 URL의 `lptag=AF...` 값 | 설정된 값과 URL 값을 정확히 비교 |
| `subId` | 등록된 채널·surface·실험 단위 실적 구분 | API 요청에 전달하고 쿠팡 리포트에서 귀속 확인 |

운영 기본 규칙:

- 현재 운영 링크에서 확인되는 파트너 추적 코드는 `AF7225079`다.
- 별도의 새 환경변수를 만들지 않고 기존 `settings.coupang.partnerId`를 추적 코드의 기준값으로 사용한다.
- Partner ID 형식은 `^AF[0-9]+$`를 통과해야 하며, 긴 제휴 링크의 `lptag`가 설정값과 정확히 같아야 한다.
- 현재 `settings.coupang.subId`의 빈 값은 의도된 설정이다. 빈 `subId`를 Partner ID로 대체하지 않는다.
- `partnerId`를 `subId`의 폴백으로 사용하지 않는다. 두 값은 역할이 다르다.
- 상품 API 호출에는 기존처럼 `subId: subId || ''`를 전달하고, Deep Link 요청에는 값이 있을 때만 body에 포함한다.
- 신규 surface별 `subId`는 쿠팡 파트너스에 먼저 등록하고 실제 리포트 귀속을 확인한 뒤에만 허용한다.
- 세션·사용자·실험군마다 임의 `subId`를 생성하지 않는다. UI 실험은 우선 내부 `experiment_id`, `variant_id`로 측정한다.
- 쿠팡 Product API가 반환한 `productUrl`은 이미 제휴 링크이므로 원형 그대로 저장하고 Deep Link API에 다시 넣지 않는다.
- Deep Link API는 순수 `https://www.coupang.com/...` URL을 관리자가 직접 변환할 때만 사용한다.
- `lptag`나 `subId`를 프론트엔드에서 문자열로 직접 이어 붙이거나 교체하지 않는다.
- Deep Link 응답의 단축 URL을 사용할 때는 같은 응답의 `landingUrl`에서 추적 코드를 검증한다.
- 최종 URL에서 `subId`가 평문 query parameter로 보이지 않을 수 있으므로, `subId`의 성공 여부는 URL 문자열이 아니라 쿠팡 리포트 귀속으로 검증한다.

### 11.2 링크 생성·검증 흐름

```text
상품 API 호출
  → 기존 설정의 subId를 그대로 전달
  → 쿠팡이 제휴 productUrl 반환
  → HTTPS와 허용 hostname 확인
  → lptag 추출
  → lptag === settings.coupang.partnerId 확인
  → 검증 성공 링크만 affiliate_links에 저장
  → /go/{link_id}에서 한 번 더 상태 확인 후 302 이동

순수 일반 URL의 예외 흐름
  → 기존 Deep Link API 호출
  → shortenUrl과 landingUrl 수신
  → landingUrl의 lptag 검증
  → shortenUrl 저장
```

허용 hostname은 필요한 쿠팡 공식 도메인만 명시적으로 등록한다. 기본 상품 이동은 `link.coupang.com`을 우선 사용하며, `coupa.ng` 같은 단축 주소는 최종 목적지를 확인한 뒤에만 허용한다.

검증 실패 시 처리:

- 링크를 사용자에게 노출하지 않음
- 상품 API가 반환한 URL이면 임의 수정하지 않고 상품 API 재수집
- 관리자가 입력한 일반 쿠팡 URL이면 기존 Deep Link API로 변환 시도
- 재변환 후에도 추적 코드가 없거나 다르면 상품을 `affiliate_link_invalid`로 격리
- 관리자 대시보드와 Slack에 상품 ID, 링크 출처, 실패 사유만 알림
- Access Key와 Secret Key는 로그·브라우저·알림에 절대 포함하지 않음

`affiliate_links` 권장 필드:

- `link_id`
- `product_id`
- `destination_url_encrypted` 또는 접근 제한된 원본 URL
- `partner_tracking_code`
- `sub_id`
- `link_source` (`product_api`, `deeplink_api`, `banner`)
- `validation_status`
- `validation_reason`
- `validated_at`
- `last_report_verified_at`

### 11.3 공통 클릭 경로

권장 방식:

```text
사용자 클릭
  → /go/{link_id}
  → 서버에서 outbound_click 기록
  → 허용된 coupang.com/link.coupang.com 목적지로 즉시 302 이동
```

장점:

- 새 탭 종료와 광고 차단기에 따른 누락 감소
- 상품·컬렉션·슬롯·실험군을 한 형식으로 연결
- 쿠팡 이외의 잘못된 목적지 차단
- 제휴 URL 변경을 중앙에서 관리
- 기존 `subId` 정책을 유지하면서 내부 surface·실험 지표 연결 가능

성능 목표는 리디렉션 추가 지연 p95 150ms 이하다.

### 11.4 일일 제휴 링크 감사

매일 상품 갱신 작업에서 다음을 검사한다.

- 노출 대상 링크 100%에 검증 완료 상태 존재
- `lptag` 누락·불일치 0건
- `subId || partnerId` 폴백 0건
- 의도하지 않은 `subid=AF7225079` 생성 0건
- 일반 쿠팡 URL을 제휴 링크로 오인한 사례 0건
- 리뷰 편집 화면에서 수동 저장한 `affiliateUrl` 검증 누락 0건
- 다이나믹 배너의 `trackingCode`와 `settings.coupang.partnerId` 불일치 0건
- `subId`를 새로 사용하는 경우에만 등록 상태와 쿠팡 리포트 귀속 확인
- 링크 생성 실패·리디렉션 실패·금지 상품 자동 격리

## 12. A/B 테스트 설계

### 12.1 배정

- `HMAC(experiment_id + anonymous_id) mod 10,000` 방식으로 안정 배정
- 같은 사용자는 같은 실험에서 항상 같은 변형을 봄
- 쿠키 사용이 불가능하면 세션 단위로만 배정
- 실제 요소가 화면에 노출된 시점부터 실험 대상에 포함
- 한 surface에서는 한 번에 핵심 변수 하나만 실험

### 12.2 노출 정의

`IntersectionObserver`를 사용해 카드 또는 CTA의 50% 이상이 최소 1초 보였을 때 impression을 기록한다.

클릭 수만 비교하면 아래 위치의 유리함을 구분할 수 없다.

- 상단이라 많이 보인 것인지
- 문구가 좋아서 클릭한 것인지
- 상품 자체가 매력적이어서 클릭한 것인지

### 12.3 현재 트래픽에서의 표본 문제

현재 거친 기준선 약 2%, 일평균 리뷰뷰 약 47회다.

- 2%에서 4%로 개선되는 큰 차이도 대략 변형당 1,100개 수준의 적격 세션이 필요
- 전체 약 2,200세션이면 현재 트래픽에서 약 47일
- 2%에서 3% 같은 작은 차이는 변형당 수천 세션이 필요

따라서 매일 승자를 바꾸면 안 된다.

### 12.4 초기 판정 기준

- 최소 14일 및 주말 2회 포함
- 변형당 적격 세션 1,000 이상
- 변형당 고유 클릭 세션 20 이상
- Beta-Binomial posterior에서 승리 확률 95% 이상
- expected loss 0.2%p 이하
- 성능·오류·EPC·취소율 guardrail 통과
- 표본 부족 시 `판단 보류`로 계속 실행

MVP 초기에는 변형당 500세션을 진단 기준으로 볼 수 있지만 자동 승격 기준으로 사용하지 않는다.

### 12.5 첫 실험 순서

1. 홈 카드의 쿠팡 직접 이동 vs 상세 경유
2. 첫 화면 큐레이션 vs 다이나믹 배너 우선
3. `쿠팡에서 현재 가격 확인` vs `구성·혜택 확인`
4. 일반 최신상품 vs 단가·가격대·배송 기준 컬렉션
5. 동일 상품 카드에서 가격 확인 시각 표시 유무

한 번에 여러 요소를 바꾸면 무엇이 성과를 만들었는지 알 수 없으므로 금지한다.

쿠팡 리포트의 늦은 반영과 정정을 흡수하기 위해 전일만 받지 않고 최근 7일을 매일 다시 upsert한다.

### 13.2 일일 보고서

일일 보고에는 다음이 포함되어야 한다.

- 어제 vs 직전 7일 및 같은 요일 기준선
- 적격 세션과 고유 사용자
- Qualified Unique Outbound CTR과 신뢰 구간
- 쿠팡 검증 클릭
- 주문·취소·순수익·EPC
- surface·카테고리·기기·유입별 성과
- 가격·링크·이미지 신선도
- 이벤트 누락·봇·중복 비율
- 진행 중 실험의 표본과 예상 남은 기간
- 개선 추천, 근거, 예상 효과, 위험, 필요한 표본
- `승인`, `보류`, `거절` 상태

### 13.3 이상 탐지

- 평소 활성 시간에 이벤트가 일정 시간 이상 없음
- 하루 전체 이벤트가 0 또는 같은 요일 기준 급락
- 봇·중복 비율 급증
- 특정 IP 또는 fingerprint 클릭 집중
- 로컬 클릭과 쿠팡 검증 클릭 비율이 평시 대비 ±50% 이상으로 2일 지속
- 실험 배정 비율 SRM 발생
- 변형별 이벤트 누락률 차이
- API 리포트 stale 또는 pagination 행 수 급변
- 가격 재관측률과 상품 매칭 정확도 저하

실제 운영 데이터에는 30일 중 이틀간 이벤트가 완전히 없는 구간이 있었지만 현재는 자동 경보가 없다. 새 시스템은 무데이터를 성과 0으로 처리하지 말고 `데이터 불완전`으로 표시해야 한다.

### 13.4 cron 안전성

- PostgreSQL advisory lock으로 중복 실행 방지
- `job_runs(job_name, business_date)` unique key
- transaction과 upsert로 재실행 결과 동일
- 실패 시 지수 백오프 재시도
- 3회 실패 또는 리포트 지연 시 Slack 경보
- DB 시간은 `TIMESTAMPTZ`, 일별 사업 기준은 KST로 명시

현재 DB는 UTC의 `TIMESTAMP`와 KST cron이 섞여 일별 경계가 9시간 어긋날 수 있다.

### 14.1 자동 처리 가능

- 이벤트 수집과 중복·봇 판정
- 일별 집계와 리포트 동기화

- 표본 부족 표시
- 깨진 링크와 명백한 품질 실패 상품의 노출 중지
- 데이터 장애, SRM, 오류율 급증 시 실험 pause
- 성능 악화 시 기존 control로 rollback

### 14.2 초기에는 사람 승인 필수

- 신규 실험 시작
- 10%에서 50%로 트래픽 확대
- 실험 승자 기본값 승격
- CTA 문구와 페이지 레이아웃 변경
- 상품 랭킹과 카테고리 운영 규칙 변경
- 알림 문구와 대상 변경

### 14.3 항상 사람 승인 필수

- 사용후기·효능·가격·재고 주장
- 제휴 고지 삭제 또는 축소
- 링크 목적지 변경
- 개인정보와 보존기간 변경
- 대량 게시·비공개·삭제
- 가격 알림의 광고성 정보 전송 범위 변경

사전 승인된 UI 변형의 자동 승격은 최소 3~5개 성공 실험과 30일 무사고 운영 후에만 검토한다. 모든 자동 변경은 즉시 rollback 가능해야 하고 감사 로그를 남긴다.

## 15. 개선 후보 추천 엔진

추천 엔진은 코드를 직접 생성·배포하지 않는다. 다음 형식의 실험 제안서를 만든다.

```text
제안: 홈 첫 섹션에서 Goldbox 8개를 가격대별로 노출
근거: 기존 홈 80뷰 대비 리뷰 랜딩 1,425뷰, 상단+이미지 클릭 75%
대상: 신규 홈 방문 세션
Primary: Qualified Unique Outbound CTR
Guardrail: EPC, 이탈, p75 LCP, 오류율
예상 효과: 방향성 추정, 보장 아님
필요 표본: 변형당 1,000 eligible sessions
위험: 얇은 상품 나열, 가격 freshness
상태: 사람 승인 대기
```

후보 점수는 다음을 함께 사용한다.

- 예상 증분 적격 클릭
- 현재 표본과 신뢰도
- 구현 비용
- 정책·신뢰 위험
- 데이터 가용성
- rollback 가능성
- 수익 지표와의 정합성

CTR만 높은 후보가 자동으로 최상단에 오르지 않도록 EPC와 정확성 guardrail을 적용한다.

## 16. 가격 하락 알림 설계

### 16.1 올바른 명칭

`최저가 알림`이 아니라 다음과 같이 표현한다.

- 이 쿠팡 상품 가격 하락 알림
- 목표 가격 도달 알림
- 최근 관측가 대비 하락 알림

표시에는 관측 시각과 `쿠팡에서 가격이 다시 변동될 수 있음`을 함께 제공한다.

### 16.2 필요한 데이터

`price_history`

- product_id
- 가능하면 item/vendorItem/option identity
- observed_price
- observed_at
- source feed
- matching confidence

`alert_subscriptions`

- 최소화된 이메일 또는 알림 채널
- 목표 가격 또는 하락률
- 동의 시각과 고지 버전
- 가격 도달 서비스 알림 동의와 제휴 프로모션·마케팅 수신 동의를 분리
- 상태와 해지 토큰

`notification_log`

- 발송·열람·클릭 시각
- 중복 방지 키
- 발송 가격
- 알림 사유
- 실패와 재시도

### 16.3 먼저 검증해야 하는 이유

현재 수집은 중복 productId를 건너뛰어 가격을 갱신하지 않는다. 임의 productId의 최신 가격을 안정적으로 다시 조회하는 흐름도 없다. 같은 productId 안에서도 옵션·판매자에 따라 가격이 달라질 수 있다.

따라서 4주간 다음을 검증한 뒤 베타 출시 여부를 결정한다.

| 조건 | Go 기준 |
|---|---:|
| 상품 재관측률 | 90% 이상 |
| 옵션·상품 잘못 매칭 | 1% 미만 |
| 표시 가격 오차 | 1% 미만 |
| 링크 유효성 | 99% 이상 |
| 알림 중복 발송 | 0.1% 미만 |

조건을 만족하지 않으면 가격 알림은 대기등록만 유지한다.

## 17. SEO와 신뢰 회복

### 17.1 기존 395개 처리

일괄 삭제는 권장하지 않는다. 검색 유입과 외부 링크를 함께 잃을 수 있다.

1. GSC·네이버 노출, 클릭, 외부 링크, 로컬 방문을 URL별로 수집
2. 상품-본문 불일치와 허위 경험·효능 표현을 자동 스캔
3. 무유입·고위험 페이지는 `noindex` 또는 비공개 후보로 분류
4. 유입이 있는 URL은 허위 후기 대신 비교·선택 정보로 교체
5. 대체 가치가 없는 URL만 관련 컬렉션으로 301
6. 모든 변경을 감사 로그와 URL 매핑에 기록

### 17.2 구조화 데이터

- 임의 `Review`와 평점 4.5 제거
- 실제 재고 정보가 없으면 `InStock` 제거
- 화면에 보이는 가격과 동일하며 신선할 때만 `Offer` 표시
- 직접 판매 사이트가 아니므로 `Product snippet` 성격에 맞춤
- 자동 생성 콘텐츠의 작성 방식과 선정 기준 공개

### 17.3 제휴 링크

Google 권장에 맞게 모든 제휴 링크에 `sponsored` 관계를 명시한다.

```html
rel="sponsored nofollow noopener noreferrer"
```

### 17.4 경제적 이해관계 공개

경제적 이해관계 문구는 사용자가 추천·CTA를 접하기 전에 명확히 보여야 한다.

- 페이지마다 CTA 아래에 여러 번 반복하지 않음
- 첫 제휴 상품 또는 첫 CTA보다 앞에 한 번만 표시
- 작은 배지나 숨김 문구가 아니라 일반 본문에서 읽을 수 있는 한 줄 사용
- 모바일에서도 생략·접힘 처리하지 않음
- 상품 카드·컬렉션·알림에도 같은 최소 고지 원칙 적용

권장 고정 문구:

> 이 페이지는 쿠팡 파트너스 활동의 일환으로, 구매 시 일정액의 수수료를 제공받을 수 있습니다.

현재처럼 상단·하단 CTA마다 문구를 반복하지 않고, 첫 CTA 전에 위 한 줄만 두는 것을 기본안으로 한다. 정책상 추가 고지가 필요한 특정 매체나 알림은 별도로 적용한다.

| 3 | 가격 확인 시각 표시 | 정보 신선도가 클릭 신뢰를 높인다 | 오래된 가격 노출 시 역효과 |
| 4 | 가격대별 컬렉션 vs 최신순 | 구매 의도가 선명해진다 | 상품 다양성 감소 |
| 5 | 단위당 가격 표시 | 반복 구매 상품의 선택이 쉬워진다 | 파싱 오류 |
| 6 | 현재가 확인 vs 구성·혜택 확인 | 과장 없는 구체 문구가 클릭을 높인다 | 상품군별 차이 |
| 7 | 비교표 3개 vs 단일 상품 | 선택 불안을 줄인다 | 정보 유지 비용 |
| 8 | 로켓 확인 상품 필터 | 긴급 구매 의도를 잡는다 | isRocket freshness |

## 21. 수용 테스트

### 이벤트

- 같은 `event_id`를 10회 보내도 1행만 저장
- 같은 세션·상품의 반복 클릭은 raw에 남지만 primary converter는 1
- CTA를 못 본 세션은 해당 CTA 실험의 분모에서 제외
- 알려진 bot과 rapid-click fixture는 qualified에서 제외
- KST 자정 전후 이벤트가 올바른 business date에 집계

### 제휴 링크

- 리뷰·홈·검색·레시피·기존 상세·신규 컬렉션 100% 공통 추적
- 목적지 allowlist 밖 URL 차단
- redirect p95 150ms 이하
- 쿠팡 `subId`가 raw 리포트와 일별 집계까지 보존
- 정상 `lptag`가 없는 URL은 노출·이동 불가
- 다른 `AF...` 값이 들어간 URL은 자동 차단
- 일반 쿠팡 URL은 Deep Link API 변환과 재검증을 통과해야만 사용
- Product API와 Deep Link API가 반환한 링크를 프론트엔드에서 재조립하지 않음
- `subId` 빈 값이 Partner ID로 폴백하지 않는 회귀 테스트
- 신규 `subId`를 도입할 때만 테스트 클릭이 쿠팡 리포트의 등록 채널로 귀속되는지 운영 전 확인

### 일일 작업

- cron 두 개가 동시에 시작해도 하나만 lock 획득
- 같은 business date 재실행 결과와 row count 동일
- D-7 정정 데이터가 기존 집계에 반영
- 리포트 미도착은 0이 아니라 stale/partial로 표시

### 실험

- 같은 사용자는 100회 요청에도 같은 variant
- SRM simulation에서 자동 pause
- 최소 표본 전 winner 불가
- control rollback 한 동작으로 복구
- partial day와 봇 데이터로 자동 승격 불가

### 추천 엔진

모든 추천에는 다음이 있어야 한다.

- 기준선과 분모
- 신뢰 구간 또는 posterior
- 예상 영향과 불확실성
- 필요한 표본
- guardrail
- 정책·데이터 위험
- 승인 상태

## 22. 성공 기준

현재 `1.96%`는 측정 계약이 불완전하므로 공식 목표 기준으로 고정하지 않는다. P1 완료 후 14일 기준선을 새로 잠근다.

초기 성공은 다음 순서로 판단한다.

1. 측정 신뢰도: 추적 커버리지와 이벤트 완전성 충족
2. 콘텐츠 신뢰도: 허위 경험·가격·배송·평점 표현 0건
3. 행동 개선: 새 Qualified Unique Outbound CTR이 control보다 유의하게 상승
4. 사업 개선: EPC와 적격 세션당 순수익이 악화되지 않음
5. 운영 개선: 매일 진단이 누락 없이 실행되고 잘못된 자동 변경 0건

90일의 방향성 목표는 CTR 숫자 하나가 아니라 다음 조합이다.

- 기준선 대비 Qualified Unique Outbound CTR의 지속적 상승
- 쿠팡 검증 클릭과 로컬 클릭의 안정적인 비율
- 주문 전환과 EPC의 동반 개선
- 가격·상품 정보 오류율 1% 미만
- 자동 진단 작업 성공률 99% 이상
- 승인 없이 발생한 위험한 콘텐츠 변경 0건

## 25. 최종 권고

CTR을 지속적으로 높이려면 버튼을 더 붙이는 것이 아니라 다음 순서를 지켜야 한다.

```text
허위·과장 제거
  → 상품 데이터 정확성 확보
  → 첫 화면에서 선택 이유 제공
  → 쿠팡 이동 단계 단축
  → 모든 노출·클릭·수익 측정
  → 매일 진단
  → 충분한 표본 뒤 실험 승격
  → 가격 이력 검증 후 알림 확장
```

세모링크의 경쟁력은 쿠팡 상품을 많이 보여주는 것이 아니라, 사용자가 지금 살 후보를 더 빨리, 더 안심하고 고르게 만드는 데서 나와야 한다.
